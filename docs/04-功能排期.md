## 二、依赖关系（为什么是这个顺序）

```
风险测评 ──────► 理财推荐 / 理财申购 / 理财赎回
                  （没做测评就申购，系统会回 INVALID_STATE —— 已实测）

收款人（已通）──► 单笔转账（已通） / AA 收款 / 送礼计划

卡片查询 ──────► 申请新卡 / 调整限额 / 锁卡 / 解锁 / 挂失

写路径泛化 ────► 上面 10 个写功能全部
（通用确认卡 + OTP 机制；现在是「转账专属」，必须先抽通用）
```

**四条排期原则**

1. **机制先行**：写路径泛化是 10 个写功能的共同前提 → **第 1 周就做掉**，否则后面每个写功能都要重复踩坑。
2. **同域成组**：容易撞车的是 `agent/classifier.py` / `agent/read_routes.py` / `agent/templates.py` 这三个**共享文件** → 同一周尽量只碰一个业务域。
3. **依赖前置**：绝不把被依赖的功能排到后面。
4. **一重几轻**：每周一个"重"（要动共享机制）+ 几个"轻"（纯读 / 纯模板），不把风险堆在一周。

## 四、每周节奏

| 时间 | 动作 |
|---|---|
| **周一** | 开工本周"重"的那一项；确认共享文件本周由谁改（避免两人同改 `classifier.py`） |
| **周三/周四** | 本周功能出一版**可跑**的（能过 `verify`） |
| **周五** | 冻结本周代码，开始写本周总结 |
| **周日** | **收束**：跑 `uv run pytest` + `bash scripts/verify.sh`（必须 6/6 全绿）→ 更新台账 → 归档当周任务卡 → 定下周范围 → 把结果同步给组员 |

**硬门禁**（每周日必须满足）：
```
uv run pytest -q          # 全绿，且不少于上周的用例数
bash scripts/verify.sh    # 6/6 全绿
```

## 五、角色与流程

- **架构与依赖顺序由「分析师」维护**：每个功能开工前，先确认它依赖的功能已就绪；接口变更必须先经人类批准（`docs/01-接口规格.md` 是规格冻结源）。
- **实现由「worker」按任务卡做**：一次只做一张卡，做完自证（贴真实命令输出）。
- **每张卡必须经「审核师」独立复跑**（含变异抽查）才计入完成。
- **人类（项目负责人）**：拍板接口变更、决定范围取舍、验收每一周的收束结果。
